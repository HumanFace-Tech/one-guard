# One Guard internal reference

This file records implementation contracts for maintainers and code agents. The user-facing installation and configuration guide is [README.md](README.md), with the details in [docs/installation.md](docs/installation.md), [docs/configuration.md](docs/configuration.md), and [docs/threat-model.md](docs/threat-model.md). Do not treat model judgment as a sandbox boundary.

## Runtime path

`plugins/one-guard/__init__.py` registers `Guard.pre_tool_call` for the native `pre_tool_call` hook. The hook accepts `tool_name`, `args`, and additional keyword metadata. It returns `None` only after a safe judgment, `{"action":"approve","message":...}` for a score inside the review band, and `{"action":"block","message":...}` otherwise. There are no per-tool exclusions, shadow mode, verdict cache, or extra plugin tools.

`guard.py` loads environment overrides over Hermes plugin config and resolves the token with Hermes' profile-aware secret API. It validates tool data, builds a bounded chat-completions or native System One request, validates the response, then applies policy. Every malformed, uncertain, unavailable, or failed judgment denies. One monotonic deadline covers capacity waiting and transport; concurrency is capped at four workers. Every socket read recomputes its timeout. Non-cancellable system DNS may retain a slot after the caller denies; never release a slot before its worker exits.

The judgment result is a typed `Outcome` (`Decision.ALLOW`, `Decision.APPROVE`, `Decision.DENY`, plus the score when one was produced), not a boolean. `judge`, `parse_verdict`, and `parse_systemone` return it, and `Guard.pre_tool_call` maps it to the hook directive. Keep the scripts and tests on that API; do not reintroduce a boolean.

The model setting is `plugins.entries.one-guard.settings.judge_model`, declared in `DEFAULTS` and `plugin.yaml`. Installer `--model` writes this key; runtime `ONE_GUARD_MODEL` overrides it and maps to internal `Config.model` and the API payload's `model`. Hermes reserves `model` as a plugin-relative key in `plugins_state._plugin_relative_segments`; never read it through `ctx.get_config`. The integration regression verifies YAML-only success and the exact model without any `ONE_GUARD_*` environment variables.

The hook gates calls delivered to Hermes' dispatcher. It is not syscall interception. It cannot see network requests, file reads, subprocesses, or other side effects hidden inside tool implementations beyond what appears in callback arguments. Hermes hooks and model judgment do not supply OS isolation.

The user selected Option 1, the normal public-API native `pre_tool_call` plugin. Scope is model-originated exfiltration attempts in hook-visible GET/POST proposals, commands, and inline scripts, in a trusted runtime/plugin environment. Supported deployment excludes post-judgment argument-rewriting hooks or middleware and hostile installed extensions. The judged proposal is not immutable final execution arguments. C1 is closed as an accepted out-of-scope limitation, not fixed. Do not add middleware, private runtime monkeypatches, or Hermes core patches to address C1. Preserve the benign peer-`modify` regression through direct dispatch and the agent executor. See ADR 0005.

## Request and response invariants

- `protocol` / `ONE_GUARD_PROTOCOL` is `chat_completions` (default) or `systemone`. The endpoint path must be exactly `/v1/chat/completions` or `/v1/systemone` respectively; no query, fragment, or embedded credentials. Never infer, fall back, or switch protocols on failure.
- HTTP is allowed by default only for literal loopback IP addresses. Hostnames such as `localhost` require HTTPS or `allow_insecure_http: true`.
- The payload includes the full bounded `tool_name` and `args`, but no conversation history. Tool argument data is untrusted prompt input.
- No argument truncation, redirect following, or ambient proxy use. Limits are 128 KiB tool data, 256 KiB serialized request, and 64 KiB response.
- Chat response requires one completed assistant choice and strict JSON content. Refusals, tool calls, malformed JSON, duplicate keys, and non-finite numbers deny.
- Chat yes/no accepts only `{"verdict":"yes"}` or `{"verdict":"no"}`. Numeric probability must be a bare JSON number in `[0,1]`; it selects one of the three probability bands.
- Native requests send full bounded `{tool_name,args}` as `state`, and exactly one `questions.risk`. Probability uses `type: noul` and true/false criteria; yes/no uses `type: choice` and yes/no criteria. See ADR 0006.
- Native response requires exactly `{model,answers,usage}`, only `answers.risk`, and documented token counters. Noul answer is exactly `{type:'noul',noul:<finite [0,1]>}`. Choice is exactly `{type:'choice',choice:'yes'|'no',probabilities:{yes:<p>,no:<p>},confidence:<p>}`. Probabilities sum to 1 within `1e-6`; inconsistent choice/max denies, ties deny, only a strictly winning `no` allows. The cutoffs apply only to probability mode. Missing/extra fields deny.
- `prompt` is appended to the built-in prompt. Operators and their environment overrides are trusted; appended instructions can contradict or weaken policy.
- Inline scripts are judged only when included in the arguments. Referenced or hidden scripts are not fetched, opened, decoded, or executed for inspection.

## Probability bands and threshold migration

Probability mode has three bands: allow below `approval_threshold`, request host approval from `approval_threshold` up to `threshold`, and deny at or above `threshold`. The defaults are `approval_threshold: 0.5` and `threshold: 0.7`; `threshold` keeps its name and now means "block at or above". The edges are exact: a score equal to `approval_threshold` is inside the review band and a score equal to `threshold` is denied. Yes/no mode has no review band and keeps its exact behavior.

`resolve_thresholds(block, approval)` in `plugins/one-guard/guard.py` and its twin in `scripts/install.py` are the only place the rule lives, and a matrix test compares them. A configured block cutoff without a configured approval cutoff keeps the legacy two-band behavior for every legacy value, so the review band stays empty and an existing installation blocks exactly what it blocked before; the approval cutoff follows the block cutoff. An approval cutoff above the block cutoff is reduced to the block cutoff, so the block cutoff always wins, that clamp never widens what is allowed, and no configuration becomes invalid. With neither cutoff configured the defaults apply.

The runtime resolves the cutoffs from the operator's values, so it must know whether a setting was configured at all: `Config.from_context` reads `threshold` and `approval_threshold` with a sentinel, and an explicitly null setting is invalid rather than unset. The installer materializes both keys, so a migrated installation is explicit in `config.yaml`. Passing `--threshold` is an explicit change to the block cutoff and returns the review band to the default `approval_threshold` of `0.5` unless `--approval-threshold` is passed too. That reset can widen what is allowed: an installation whose approval cutoff was below `0.5` will allow the scores between that cutoff and `0.5` instead of sending them to the review band. It is an operator-selected reset, not a property of the clamp, and the installer shows the effective band on the review screen before it writes anything.

The review band is a request, not a decision. Hermes owns the approval gate, so `approvals.mode: off`, the YOLO toggle, unattended approve modes, and the session or permanent allowlists can approve a mid-band call without a human; the operator accepted that host policy. The plugin must not try to override it, and it must not claim that a mid-band call always reaches a human. The plugin sets an explicit `rule_key`: a namespaced `one-guard:<sha256>` digest over the full validated bounded `{tool_name,args}` proposal, so a remembered `session` or `always` answer applies to that exact proposal and not to every later review-band call for the same tool. Hermes substitutes the bare tool name when a plugin returns no `rule_key`, and that fallback also covers approvals other plugins request for the same tool, so the plugin always sets its own. The score is not part of the digest: the score decides whether a proposal enters the band, the host owns what happens there, and a score that moves between runs must not fragment a remembered answer. A proposal that cannot be serialized denies instead of reaching the gate under a coarser key. The digest identifies the proposal as judged, so a peer `modify` hook that rewrites arguments afterwards remains the unsupported configuration of ADR 0005. The namespace scopes an answer only when the plugin's own approval is the one the host keeps: Hermes takes the first valid `approve` directive of a call, so a peer plugin that asks for approval first takes precedence and its rule key is the one remembered. The approval message carries the score and the band and never carries tool arguments, credentials, or judge response bodies. The review band needs a host that understands the `approve` directive; the plugin targets the pinned Hermes revision. See ADR 0008 and ADR 0009.

TypeSafe System One's Noul probability output is not interchangeable with a generic LLM-generated numeric score. Neither protocol has a calibration guarantee. Initial live smoke timed out in all six cases at 10 seconds. Later full live smoke runs passed six synthetic cases in both probability and yes/no modes with a 60-second deadline; each request took about 19.5 to 21.9 seconds. These twelve outcomes are not proof of broad classification efficacy, calibration, or prompt-injection resistance. See [the verification record](docs/verification.md#live-endpoint-observations) for commands and cases. Timeout default remains 5, with a supported range of 0.01 through 120 seconds. Installer `--timeout` preserves existing settings when absent. Warn if the configured/preserved timeout reaches or exceeds Hermes' `plugins.hook_callback_timeout` (default 30), recommending at least timeout + 5 seconds; never change that global setting. A 60-second plugin timeout needs a separate Hermes host timeout of at least 65 seconds. Host timeout 0 is unlimited and needs no warning. The opt-in `scripts/smoke-systemone.py --run-live` sends synthetic proposals only and never executes them. Normal automated tests use a local stub.

## Installer invariants

`install.sh` dispatches to `scripts/install.py` with Python 3. The installer selects Hermes source separately from Hermes data home; it can discover a source from `HERMES_DIR`, the executable, and common locations. Ambiguity requires an interactive selection or explicit `--hermes-dir`, including with `--yes`.

`scripts/install.py` imports `scripts/installer_ui.py` and `scripts/installer_bootstrap.py` through `importlib` by path, not as packages, so all three files must stay siblings and must not rely on relative imports. `installer_ui` owns terminal rendering. `PlainUI` is the always-available fallback; `ToolkitUI` uses `prompt_toolkit` for arrow-driven menus, masked input, and inline validation. `create_ui` requires a TTY on stdin and stdout. `--plain`, `--yes`, `TERM=dumb`, or any set `NO_COLOR` disables enhanced UI selection and bootstrap. If the UI is missing, the installer asks before source selection before downloading its pinned requirements into a temporary isolated virtual environment. `installer_bootstrap.provision()` removes that environment on exit and cleans its imports. It installs only the optional UI packages, not PyYAML/python-dotenv, Hermes, or runtime dependencies, and does not modify system Python or Hermes. Declining or failing to provision keeps the plain wizard available.

The wizard flow is: source selection, data home, judge connection, decision policy, authentication, optional model discovery, review. Every step is re-entrant from the review screen. `run_wizard` returns only after the user confirms. Cancel, Ctrl-C, and EOF raise `Cancelled` before any filesystem write, so the target home is never created. `--yes` skips `create_ui` entirely, never prompts, and never probes the judge.

Model discovery is explicitly opt-in and runs after authentication. Before consent, the wizard identifies the same-origin `GET /v1/models` request and whether the credential selected by this installer will be sent. That credential is the one stored in the Hermes `.env`; Hermes resolves the runtime credential from its own profile and environment, so the runtime value can differ and the installer must not claim otherwise. A remote plaintext HTTP endpoint is called out as carrying the credential unencrypted, or, without one, as exposing the request; a literal loopback address is not reported as remote. `probe_models` makes a single direct request: no redirects, pagination, ambient proxy, or additional downloads; it has a five-second deadline, a 64 KiB response cap, and displays at most 64 sanitized identifiers. The request carries the scheme's default `Host` header, so the default port is omitted. The credential is threaded into the parser, so identifiers that carry it are dropped before the identifier limit and the truncation flag are computed. Name resolution is not cancellable, so a worker blocked in system DNS keeps its probe slot until the lookup returns, which can outlast the five-second deadline; the slot is never released before the worker exits. Identifiers containing the selected credential anywhere are dropped before the list is shown, so a hostile judge cannot steer the credential into `judge_model`; the rule is conservative and suppresses false positives for short credentials. Discovery identifiers are stripped of surrounding whitespace, then dropped if they contain any Unicode C-category character (including controls, format characters, surrogates, private-use, and unassigned code points); installer validation likewise rejects C-category characters in configured endpoints and models. This is an installer rule, not a matching runtime guarantee: runtime `Config.validate` does not apply that C-category check to the model or endpoint, so direct YAML edits and environment overrides can bypass it. The identifier limit counts usable identifiers, so entries dropped as invalid, duplicated, or credential-bearing do not consume it. A deeply nested response body falls back to manual entry without writing anything. Failure, offline service, or unusable response falls back to manual model entry/endpoint default. The wizard reports server metadata only: for `systemone`, native decisions are claimed only when the exact value `decisions` is listed in `architecture.output_modalities` and text-only only when that list is exactly the single value `text`; matching is exact, so a differently cased or padded value does not count, and every other combination and any malformed value is unknown. Chat-completions entries are labeled as compatibility not declared. None of these labels verifies actual compatibility. If the discovery endpoint is remote HTTP, the explicitly confirmed request transmits the credential in plaintext when one is present. Installer tests exercise the discovery request against a loopback stub, including TLS certificate verification; do not claim live model-list or compatibility evidence.

If `effective_credential` cannot resolve the selected credential at the model step, discovery makes no network request and offers manual model entry with a generic warning and a blank default. Malformed `.env` files or read errors may instead abort earlier during authentication or configuration loading. Do not treat resolution failure as credential absence or echo exception details or the unresolved model default. A valid manual model can repair an invalid existing `judge_model`; other configuration or credential errors still prevent installation.

Validation lives in the installer, not only in the UI: `validate_source`, `validate_home`, `number_field`, and the endpoint and model checks reuse `merge_config` with a throwaway `argparse.Namespace`, so the wizard and the CLI apply identical rules. `trial_args` builds that namespace. Endpoint failures in the wizard mention the transport-policy step instead of CLI flags, via `endpoint_error`.

Terminal output passes through `installer_ui.safe_text`, which escapes control characters, and `UI.clean`, which replaces known secrets with `[credential]`. Never print a token, and never echo one from a validation error. The review screen reports credential presence only.

Installer `--protocol` selects the explicit protocol. First-install default endpoint follows that selection; existing endpoints are preserved and must match. `--allow-insecure-http` enables first-install LAN HTTP without preexisting YAML. No inference server, model, or Hermes installation is performed.

The installer writes both `threshold` (the block cutoff) and `approval_threshold` into the plugin settings on every run, and the review screen shows the effective band. A `--yes` run prints the same band as one line, `Risk band: allow below X, review X to Y, block at Y and above`, or `Risk band: not used in yes/no mode`; it carries the two cutoffs only, no tool data, credential, or judge body. A legacy installation with a configured `threshold` and no `approval_threshold` keeps its exact old behaviour: the approval cutoff follows the block cutoff, so the review band stays empty and the migrated state is explicit in `config.yaml`. `--threshold` is an explicit change to the block cutoff and returns the review band to the default `approval_threshold` of `0.5` unless `--approval-threshold` is passed too; that reset applies even when the installation already held an `approval_threshold`. An approval cutoff above the block cutoff is reduced to the block cutoff. One function, `threshold_sources` in `scripts/install.py`, decides which configured value each cutoff comes from, and both the installer merge and the wizard defaults use it.

PyYAML and python-dotenv must already exist in the current interpreter or Hermes `.venv`; the installer does not install them. Only after explicit consent, the optional UI bootstrap runs pip inside a temporary isolated virtual environment with pinned, hash-checked UI requirements; it cleans that environment on exit. Settings merge into existing YAML; comments/formatting may change. Absent `plugins.enabled` on a pre-v21 stamped config preserves upstream top-level user-plugin grandfathering, excluding disabled manifest names. Modern configs remain opt-in. Unversioned configs with installed plugins and ambiguous legacy layouts require explicit enablement before writes. Unsafe YAML, symlinks, hard links, unowned target directories, and changed ownership hashes stop installation. Written files use `0600`, new directories `0700`; existing directory permissions stay unchanged. Atomic per-file replacement uses a random backup directory and rolls back plugin/config/`.env` on failure. Installer code is POSIX-oriented (`fcntl`).

The token comes from `ONE_GUARD_TOKEN` or a hidden interactive prompt and is written to Hermes `.env`. The manifest declares `type: secret`, `env: ONE_GUARD_TOKEN`; dashboard fields expose presence only. Without a supplied token, preserve `.env` or migrate a legacy YAML token, removing that YAML setting. Reject ambiguous token assignments and `${` interpolation. Backups can contain credentials. No `--token` argument is offered. Never add secrets to logs, manifests, errors, or examples. A model identifier typed by hand stays the operator's own choice; the installer warns when it contains the selected credential, because that credential would then be written to `config.yaml`.

## AI-assisted rollout

Read the README and inspect the target environment before helping with installation. Confirm with the human which Hermes source checkout, data home, judge endpoint, and model to use. Do not install Hermes, an inference service, or a model as part of this plugin setup.

Ask the human to enter credentials directly in the masked wizard prompt; do not request, display, or log them in chat. Obtain explicit approval before enabling plaintext HTTP to a remote judge: tool arguments and credentials would travel unencrypted. The human can operate the wizard in a terminal; `--yes` is available for explicitly approved non-interactive setups.

Explain and obtain approval before changing Hermes' global `plugins.hook_callback_timeout`. The installer warns but does not change it. Stop or restart Hermes only with the operator's approval. Verify plugin loading and safe/denied behavior with inert proposals, without executing suspicious commands or contacting their embedded destinations. The guard is not a sandbox; post-judgment rewriting hooks are unsupported, and the live judge previously allowed a guard-removal proposal.

## Documentation and verification ownership

The ADR system in `docs/adr/` is public and visible to everyone, as is this repository. Before writing or updating an ADR, review it for disclosure: never include credentials, tokens, private endpoints or network addresses, identifying local paths, personal data, confidential infrastructure details, or private incident material. Use fictional placeholders and public sources where needed; record the architectural decision without carrying sensitive deployment details into the ADR. Review existing and changed ADRs before publication.

Keep README configuration names and constraints synchronized with `DEFAULTS`, `Config.validate`, `plugin.yaml`, and `merge_config`. Keep installation steps synchronized with `scripts/install.py`, `scripts/installer_ui.py`, and `install.sh`. Document test scope, not only test commands. [docs/verification.md](docs/verification.md) records executed Hermes-runtime integration results; do not invent results or claim that stub tests establish model efficacy.

Wizard changes need a real terminal check, not only mocked input. `tests/test_installer_terminal.py` drives the installer through a pseudo-terminal with arrow keys and asserts the resulting `config.yaml`. `tests/test_installer_wizard.py` covers the flow logic with a scripted UI. Keep both: the scripted tests are fast, and the pseudo-terminal tests catch rendering and keybinding regressions that mocks cannot.

See [ADRs](docs/adr/README.md) for accepted design decisions. Documentation must not silently change the project's scope or implementation claims.
